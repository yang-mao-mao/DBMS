# B+ 树索引模块开发报告

## 一、任务与范围

本项目已有两项经过测试的基础能力：`storage/` 负责磁盘页，`buffer_pool/` 负责页面在内存中的缓存。
索引模块的目标是复用这些能力，把“按业务键查找记录”变成“沿少量索引页面定位 RID，再读取数据页”，
而不是替换原有磁盘管理器或缓冲池。

本轮所有源码、测试、构建配置和文档均放在 `index/`。
没有修改 `storage/`、`buffer_pool/`、项目根目录 `CMakeLists.txt`，没有引入第三方树容器。
这也意味着根工程的 `db_test` 主程序尚未自动集成索引，需要上层后续调用这些接口。

### 已实现与未实现

| 能力 | 状态 |
| --- | --- |
| 唯一整数键、RID 定位 | 已实现 |
| 多层等值查询、插入、叶子与内部节点分裂 | 已实现 |
| 根分裂和根页号持久化 | 已实现 |
| 范围扫描、无界扫描、结果条数限制 | 本轮新增 |
| 删除、双向借位、双向合并、根收缩 | 本轮新增 |
| 废弃页回收和空闲页复用 | 本轮新增 |
| 正常保存并关闭后重新打开 | 已测试 |
| 跨数据页与索引的原子事务、WAL、崩溃恢复 | 未实现，见第十三节 |
| 并发访问、SQL 优化器、系统目录自动发现索引 | 未实现 |

这里的“删除”是删除索引项，不是删除业务记录；“可以重启读取”是正常保存后的持久化，
不等于程序被强制结束或断电后具备恢复保证。

## 二、从什么结构开始

### 2.1 索引键与记录位置分开

第一版选择 `IndexKey = std::int64_t`，由上层决定它代表学号、记录编号还是其他整数列。
叶子项是 `key -> RID{page_id, slot_id}`，例如：

```text
1001 -> RID{8, 3}
```

含义是：先用索引找到键 1001，再通过缓冲池取第 8 页，最后调用 `get_record(3, length)` 读取记录。
索引不解析业务记录，也不验证该 RID 对应的记录是否真的存在。

选择 RID 而不是字节偏移或内存指针的原因，是原数据页已经采用槽目录。
页内 `compact()` 可以移动记录字节，但槽号不变；缓冲帧则可能随时被淘汰、复用，不能作为持久地址。
`purge_deleted_slots()` 会改变槽号，不能在不修正索引的情况下用于被引用的数据页。

### 2.2 模块分层

```text
上层查询 / 记录管理
        |
        v
BPlusTree：索引逻辑
        |
        v
BufferPoolManager：fetch / new / unpin / delete
        |
        v
DiskManager：页面分配、读写和空闲页管理
```

索引逻辑不直接打开文件，所有实际索引页面都经过缓冲池。
缓冲池已有的“页号 -> 帧下标”哈希表继续保留，B+ 树负责的是另一层“字段值 -> 记录位置”。

## 三、为什么不直接调用内存树容器

本模块需要控制节点页号、页面格式、缓冲池 pin/unpin、脏页和重启读取。
一个只管理内存节点与指针的有序容器，并不会自动接入这些项目接口。
因此这里直接实现页面化索引，而不是在内存容器外加一个名称就当作数据库索引。

实现中使用 `std::vector` 暂存解码后的节点，使用 `std::map` 管理待修改页面，
但它们只是辅助结构。业务键的持久化组织与路由由磁盘 B+ 树完成，
不是把所有索引项保存在一个 `std::map` 中。

## 四、页面格式与容量

### 4.1 沿用原槽页

一个 B+ 树节点对应一个 `PageType::INDEX` 页面，把整个节点编码为槽 0 的一条记录。
这样不必改动原有 `Page::validate()`、记录边界校验和页面校验和逻辑。
写入先在临时 `Page` 中清空并重建记录，成功后才替换待写页面副本。

不直接把包含 `std::vector` 或填充字节的 C++ 结构体写入磁盘。
记录内部按字段进行小端编码，负数键使用位表示转换。
外围 `PageHeader` 的格式仍沿用原存储实现，不能据此宣称整个数据库已经跨平台可移植。

### 4.2 叶子页

节点头 20 字节：魔数 4、版本 2、类型 2、数量 2、保留位 2、父页号 4、后继叶子页号 4。
每项占 14 字节：键 8、RID 页号 4、RID 槽号 2。

```text
最大叶子项数 = floor((4096 - 48 - 6 - 20) / 14) = 287
```

这里减去的 48 字节是原页面头，6 字节是一个槽。
**287 只是单个叶子页面的容量，不是整个索引的上限。**

### 4.3 内部页

内部页也使用 20 字节节点头，但类型为 2，头部最后 4 字节改为第一个子页号。
后续每项占 12 字节：分隔键 8、该键右侧子页号 4。

```text
最大分隔键数 = floor((4096 - 48 - 6 - 20) / 12) = 335
最大子页数   = 336
```

内部节点不保存业务 RID，只保存分隔键与子页号。
有 N 个分隔键，必须有 N+1 个不同的合法子页号。

### 4.4 索引头页

独立头页记录长 12 字节，保存魔数、版本、头页类型和根页号。
不使用第 0 页，因为第 0 页由 `DiskManager` 管理。
根分裂或根收缩后修改这个头页，而不是要求上层追踪不断变化的根页。

调用方仍须保存稳定的 `header_page_id`；目前没有系统目录自动发现索引。

## 五、开发过程分为三个阶段

### 第一阶段：验证底层接入

先定义 RID 和单叶子节点格式，实现“节点写入槽页 -> 经缓冲池保存 -> 关闭后读取”。
这一阶段只有一个叶子页，满页返回 `PAGE_FULL`，作用是验证页面布局与持久化接口。
它不是完整的多层 B+ 树，也不能用来说明大数据量查询优化已经完成。

### 第二阶段：去掉单页总容量限制

增加内部节点、从根到叶子的路由、叶子分裂、内部节点分裂、分裂向上传播和新根创建。
页满不再作为容量终点，而是触发结构扩展，取消了第一阶段的 `PAGE_FULL` 返回值。
通过正常插入 10 万项、6 万项，验证实际形成三层树，而不是只验证几个内存节点。

### 第三阶段：补齐有序扫描与删除维护

在已经维护好的叶子链上增加范围扫描。
删除则复用路径、页面副本和父页号，在删除后处理节点不足、分隔键更新和页面回收。
这些改动没有改变原单叶子记录或索引头记录的编码版本，旧索引可正常打开并继续扩展。

## 六、等值查询怎样工作

1. 从索引头页读取当前根页号，避免其他句柄改变根后使用旧根。
2. 内部节点使用 `upper_bound` 选择子页。
3. 在叶子节点使用 `lower_bound` 定位键，再检查是否相等。
4. 找到则返回 RID；未找到或页面错误时，不覆盖调用方原 RID。

例如内部节点分隔键为 `[30, 60]`：

```text
子页 0：key < 30
子页 1：30 <= key < 60
子页 2：60 <= key
```

因此键等于 30 时要走右侧子页，不能把 `upper_bound` 随意换成 `lower_bound`。
查询路径还检查页号身份、父子关系、键范围和重复访问页面。
这只检查实际经过的路径，不是一次全树审计。

## 七、插入和分裂怎样工作

### 7.1 普通插入

沿路径找到叶子，拒绝重复键，在有序位置插入键与 RID，编码页面副本后提交。
原业务记录由上层管理，索引插入不会替上层插入数据记录。

### 7.2 叶子分裂

插入后超过 287 项，就把 288 项分成左右两组，各 144 项。
左页保留原页号，新分配右页；右页继承原来的后继，左页后继改为新右页。
把右页首键**复制**到父节点作为分隔键，叶子中仍保留这条真实索引项。

### 7.3 内部分裂

父节点也满时，取中间分隔键提升到上层。
该键不留在左右内部节点中，两侧保留相应分隔键及子页。
搬到右节点下的所有子页，都要把父页号从旧页改为新右页。

### 7.4 根分裂

分裂传播超过原根时，新建一个内部根，连接左右子页，并更新两者父页号。
最后把新根页号写入索引头页。正常保存之后，上层只需保存头页号即可重新打开。

## 八、范围扫描怎样工作

### 8.1 接口约定

```cpp
std::vector<BPlusTreeLeafEntry> entries;
const auto result = tree->scan(1000, 2000, entries, 100);
```

含义为：按键升序返回 `[1000, 2000)` 中最多 100 项。
上下界是可选值，`scan({}, {}, entries)` 表示无界扫描。
这种设计可以包含 `INT64_MAX`，而不需要计算会溢出的“最大整数加一”。

下界大于上界返回 `INVALID_RANGE`；上下界相等或 `limit == 0` 直接返回成功空结果，不访问树。

### 8.2 扫描流程

```text
从根定位 lower 所在叶子
          |
          v
从 lower_bound 开始读取
          |
          v
沿 next_page_id 进入下一叶子
          |
          v
达到上界、条数限制或链尾时结束
```

不是枚举区间内每个整数后分别调用 `find()`，也不扫描不相关的所有索引页。
成功时一次性替换输出向量；遇到访问错误、循环链或顺序异常时，保留原输出，不暴露部分结果。
这些校验不能证明叶子链绝无缺页或跨索引链接，完整校验仍需更强的结构审计。

当前结果保存在向量中，内存成本随返回条数增长。默认不限制数量，
所以大范围查询建议显式传 `limit`；当前没有流式游标或并发快照保证。

## 九、删除、借位和合并怎样工作

### 9.1 维持哪些不变量

- 同一叶子的键严格递增，索引键唯一。
- 所有叶子深度一致，叶子链与树的中序顺序一致。
- 每个内部键等于对应右子树的最小键。
- 子页记录正确父页号，根父页号为 `INVALID_PAGE`。
- 非根叶子至少 144 项，最多 287 项。
- 非根内部节点至少 167 个分隔键，最多 335 个。
- 空索引保留一个空叶子根，内部根不能只有一个子页而长期不收缩。

### 9.2 普通删除也可能需要更新父节点

先定位叶子，找不到键返回 `NOT_FOUND`，不修改页面。
删除成功后，即使叶子仍够满，如果删除的是首键，父分隔键也可能需要更新。
若变动沿连续的最左子树向上传递，还要继续检查祖先边界，而不只修改直接父节点。

### 9.3 先尝试借位

节点低于下限时，先检查同父左兄弟，再检查右兄弟。
兄弟超过最小占用量时，可借一项或一个子页，避免合并。

叶子借位移动的是实际键与 RID，然后刷新父节点边界。
内部节点借位移动的是子页；父分隔键参与下移、兄弟分隔键参与上移，
不是简单移动一个键就结束。移动子页后还必须更新其父页号。

### 9.4 无法借位再合并

优先把当前节点合入左兄弟；没有左兄弟时，让当前节点吸收右兄弟。
叶子合并连接记录并修复后继链，不把父分隔键当成额外数据记录写入叶子。
内部合并则要把父分隔键夹在左右分隔键之间，并调整移动子页的父页号。

父节点移除一个分隔键与一个子页引用。如果父节点也不足，就逐层重复修复。
删除只从树根向叶子寻路一次，随后沿保存的路径向上处理，不重新扫描全表。

### 9.5 根收缩与删空

内部根只剩一个子页时，把该子页提升为根，父页号改为 `INVALID_PAGE`，并更新索引头页。
旧根成为待回收页。所有项删完后，保留空叶子根和头页，可以继续插入。

### 9.6 页面回收不能与逻辑删除混淆

结构提交成功后才调用缓冲池 `delete_page()` 释放废弃索引页。
释放成功后，它进入磁盘空闲链表，可被后续索引分配复用；这不会自动缩短数据库文件。

`erase()` 返回值有四种：

| 返回值 | 含义 |
| --- | --- |
| `REMOVED` | 索引项删除，废弃页回收成功 |
| `NOT_FOUND` | 未找到该键，没有删除 |
| `PAGE_ERROR` | 页面访问、格式或结构提交失败；不具备任意故障下的原子性保证 |
| `RECLAIM_FAILED` | 逻辑删除已经提交，但有废弃页未能回收 |

例如，外部仍 pin 住旧根时，根收缩可以成功，但旧根不能立即释放。
因此 `RECLAIM_FAILED` 不能解释为“删除没有发生”。当前没有持久化回收重试队列，
可能遗留不可达页；需要上层关注此状态，避免长期 pin 索引内部页。

## 十、怎样复用缓冲池并处理失败

### 10.1 PagePin

索引每次通过缓冲池拿到页面就构造 RAII pin 守卫，退出作用域时自动 unpin。
页号使用请求的页号，不依赖可能损坏的页头身份字段。
不会在 unpin 后保留 `Page*` 继续使用，而是复制必要内容到临时对象。

因此包括分裂、内部合并在内，不要求一次把所有涉及页面同时 pin 在缓冲池中。
测试覆盖只存在一个缓冲帧的情况；临时页面副本占用的是普通进程内存，并非额外缓冲帧。

### 10.2 PageChanges

多页修改通过暂存对象组织，保存页面原副本、修改后副本、新分配页和待退休页。
在提交前检查涉及页面是否可读、是否仍与原副本一致，然后写新节点和其他修改，头页最后更新。

提交前发现错误时，不把修改后的旧节点写回；新分配页面尽力释放。
提交途中失败时，尝试逆序恢复已经替换的页面。恢复也失败时，保留新页，
而不是直接释放可能已经被引用的页。
删除废弃的旧页只在逻辑结构提交成功之后释放，避免提交失败时原树仍引用已释放页面。

这些是错误处理和资源管理措施，**不是 ACID 事务，也不是崩溃恢复**。
真实 I/O 失败、内存分配异常或进程中断可能造成部分更新与遗留页面。

## 十一、测试是怎样组织的

采用现有项目的 CMake/CTest 风格，不另加测试框架。
Release 构建保留测试断言；每个测试使用独立临时数据库，不覆盖项目中的 `page_test.db`。

### 11.1 原索引测试：20 项

`b_plus_tree_test.cpp` 验证页面编解码、错误记录、容量边界、插入查询、
叶子与内部节点分裂、根变化、单缓冲帧、多索引隔离、多句柄、重启和失败路径。

其中 10 万项正序、6 万项逆序测试通过实际逐项插入生成树，并逐项查找，
检查高度、占用量、分隔键、父指针和叶子链。
这些测试证明所测场景可扩展到多页、多层，不等于任意数据与故障场景都已形式化验证。

## 十二、效率应该怎样理解

设树高为 h，扫描经过的叶子页数为 L，返回项数为 k。
等值查询沿一条路径，节点页访问数随 h 增长，另外会访问头页；
范围扫描在路径定位后顺序访问匹配叶子，主要节点访问量随 h+L 增长，并需要存放 k 项结果。

这里说的是页面访问，不等于物理磁盘 I/O 次数：缓冲池命中时不需要再读磁盘。
当前每页会完整解码和校验；内部节点合法性检查也有开销，不能只看到二分查找就忽略这些成本。
内部合并或分裂还可能修改许多移动子页的父页号，不是只写固定两个页面。

目前未在相同记录布局、缓存状态与查询负载下完成全表扫描对比，
所以报告不提供“提升多少倍”的结论，也不把整个测试套件耗时当成一次查询延迟。
后续应分别测量点查、范围查询、插入和删除，并区分冷缓存与热缓存。

## 十三、为什么没有把事务恢复也宣称完成

### 13.1 当前能够保证与不能保证的事情

当前测试确认正常执行、显式刷新、关闭后重新打开的行为。
内存页面副本只能在进程仍运行时用于尝试回滚；进程消失后，这些副本也消失。
分裂、合并和根变化涉及多页，崩溃可能发生在其中任何一步。
正常关闭测试通过，不能推导出突然断电后一定一致。

### 13.2 后续恢复设计需要协作的接口

1. 定义持久日志管理器，明确日志记录、事务边界和可靠落盘方式。
2. 根据选定恢复策略记录页修改及必要的页分配、释放与元数据变化。
3. 使用页面 LSN，并在缓冲池淘汰或显式刷盘前遵守日志先于对应页面持久化的约束。
4. 定义提交与回滚行为，协调业务数据和索引，避免只恢复其中一方。
5. 启动时执行所选策略需要的重做、撤销或其他恢复流程；不能仅凭文件存在就视为恢复成功。
6. 再设计检查点、日志回收、页撕裂处理和断电/故障注入测试。

这是后续设计方向，不是已经实现的 API。具体是否需要撤销、何时允许刷脏页，
取决于先确定的事务与缓冲策略，不能简单加一个文本日志文件就宣称完成事务恢复。
`fstream::flush()` 也不能直接等同于已经验证了断电后的设备持久性。

恢复协议必须覆盖磁盘分配与释放、元数据、缓冲池刷盘以及上层事务。
在“本轮不改动现有存储和缓冲池”的约束下，不能只修改 `index/` 就承诺整个数据库恢复正确。
当前也没有执行崩溃恢复测试，报告不虚构这类结果。

## 十四、建议怎样阅读源码

1. 先读 `RID.h`，理解索引值为何是记录位置。
2. 读 `BPlusTreePage.h`，理解两类节点、容量和最小占用量。
3. 读 `BPlusTreePage.cpp`，理解实际写盘字段及失败时不修改输出的编码规则。
4. 在 `BPlusTree.cpp` 中先看 `read_path()`、`find()`，再看 `insert()` 和 `propagate_split()`。
5. 然后读 `scan()`，对照叶子链理解范围查询。
6. 读 `erase()`、`repair_after_erase()` 及借位合并辅助函数，注意父分隔键与真实叶子项的区别。
7. 最后看 `PagePin`、`PageChanges` 和两份测试，理解算法之外的页面生命周期与错误处理。

如果上层开始支持业务记录的删除和更新，还需要明确数据记录与各个索引的更新顺序、
失败补偿和将来的事务边界。不能把孤立的 `erase()` 当作整条 SQL DELETE 已经完成。
